## 1. The pitch

### Problem

Physical AI is moving from labs into real deployments, and two things are true at once:

- **Requirements are exhaustively documented.** PLM systems, safety cases and requirement trackers define what a machine must do, often under regulatory obligation.
- **Testing against those requirements is manual and disconnected.** Telemetry produces a *symptom* ("joint overshoots", "gripper slips under load", "gait destabilizes on incline"). An engineer then reads logs, recalls institutional knowledge, and maps the symptom to the requirement it violates and the known issue behind it.

That mapping step is where:
- the time goes
- tribal knowledge lives, and breaks when the engineer who knew it leaves
- scale fails: test suites and fleets produce more symptoms than engineers can triage, and every hardware revision resets the knowledge

### Solution

An agent holds the requirements as durable memory and queries the live machine directly through its middleware. When a test fails, it returns, with a citation for each:

| Output | Example |
|---|---|
| Requirement violated | requirement ID |
| Root cause | e.g. sensor bias |
| Fix | the action to apply |
| Known-issue tag | link to the known issue |

**Citation is the product, not a feature.** In safety-critical hardware, an uncited diagnosis is unusable.

## 2. The proof of concept

Validated end-to-end on a **self-driving car's steering subsystem**, chosen because it could be simulated, fault-injected and validated in 12 hours. The steering use case is scaffolding, not the target market.

| Part | What it does |
|---|---|
| Live system | A real ROS 2 control stack with a fault injector: 5 fault modes (bias, reversed, stuck, noise, lag) |
| Symptom detection | A pure, unit-tested classifier compares commanded intent with measured response over a rolling window. It emits a symptom and a health status, never a root cause. 12 tests, one per decision branch |
| Agent access | An MCP server exposes the system as tools: read health, read stats, inject fault, restart unit |
| Requirement memory | Requirements and known issues held as durable agent memory, mapped from symptom to requirement ID, root cause, fix and known-issue tag |
| Closed loop | A web panel shows live telemetry, the cited diagnosis and a one-click fix that round-trips through the real stack until the test flips to PASS |

**Design choice to keep:** the fault injector is named like a production ECU, so the agent can't shortcut the diagnosis by reading node names. It has to reason from the signal.

## 3. Open questions (from the PDF)

| Question | Detail |
|---|---|
| Requirement ingestion | Most requirements live in unstructured Word, Jira, Confluence and PDF. Is ingestion an onboarding step, or is it the actual product? |
| Where the value lands | Pre-deployment testing and CI, or deployed-fleet triage? Different products. |
| Classifier scaling | Reliable, low-false-positive symptom classifiers are the hardest and most defensible asset. If they need rebuilding per customer and per subsystem, is this a product or a consultancy? |
| Deployment model | On-prem or self-hosted is probably mandatory given IP sensitivity. What does that cost in iteration speed? |
| The honest one | Would a team just prompt an LLM with their requirement doc and logs and get 70% of this for free? Current answer: determinism, live system access and citations an auditor will accept. Untested. |
